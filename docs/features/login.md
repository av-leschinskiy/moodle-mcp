## Как устроено

Сервер вызывает REST API веб-сервисов Moodle с токеном пользователя. Токен выдаёт сам сайт
тем же путём, что мобильному приложению Moodle: сервис `moodle_mobile_app`, страница
`admin/tool/mobile/launch.php`. Поэтому подходит любой вход, который сайт показывает
в браузере, — пароль, внешний OAuth-провайдер, капча.

Как войти:

1. Запустить `moodle-mcp-login` с `MOODLE_URL` — адресом сайта в точности как в браузере,
   со схемой и путём. Команды запуска для клона и для `npx` — в README, «Быстрый старт».
2. Откроется окно Chrome с отдельным профилем. Войти на сайт как обычно: пароль и капчу
   вводит человек. Команда ждёт входа и называет в терминале время, до которого ждёт.
3. Сайт переходит по адресу возврата с токеном. Команда проверяет токен, сохраняет его
   в файл `MOODLE_TOKEN_FILE`, закрывает окно и печатает «Вошёл как <имя> на <сайт>».

Перезапускать MCP-сервер после входа не нужно: файл токена сервер читает при каждом
вызове API.

Входить заново нужно, когда тул отвечает ошибкой с `kind: auth`: токен истёк или отозван,
срок его жизни задаёт сайт. И при смене сайта: в файле один сайт, и сервер с другим
`MOODLE_URL` отказывает с подсказкой войти. Профиль Chrome хранит cookies сайта, поэтому
повторный вход может пройти без пароля.

`MOODLE_TOKEN` подменяет файл — для CI и смок-проверок, где окна нет.

## Инварианты

- **Токен не выводится** ни при каком исходе: ни в терминал, ни в текст ошибки. Ошибки
  разбора не цитируют адрес возврата — в нём токен. Файл токена — с правами только
  владельца, запись атомарная.
- **В файл попадает только проверенный токен:** подпись ответа совпала с адресом сайта
  и passport этого входа, а вызов `core_webservice_get_site_info` прошёл. Иначе прежний
  файл остаётся нетронутым: файл с нерабочим токеном хуже, чем его отсутствие, — сервер
  отвечал бы невнятным `invalidtoken`.
- **Форма входа не заполняется программой.** Команда только открывает страницу и ждёт
  перехода с токеном: капча сайта рассчитана на человека.
- **Токен действует от имени вошедшего.** Тулы видят и меняют ровно то же, что этот
  пользователь в веб-интерфейсе; права проверяет Moodle.

## Почему так

- **Мобильный сервис**, а не отдельный веб-сервис: он включён на большинстве сайтов и выдаёт
  токен самому пользователю. Отдельный сервис с токеном завёл бы только администратор сайта.
- **Не `login/token.php`.** Он меняет логин и пароль Moodle на токен, а у входа через
  внешнего OAuth-провайдера пароля Moodle нет, и капчу там проходит только человек.
- **Перехват через протокол отладки Chrome.** Moodle возвращает токен переходом на схему
  приложения (`moodlemobile://`), которую браузер не открывает. Команда читает этот переход
  из навигации браузера, а не из ответа сервера.
- **Подпись `md5(адрес сайта + passport)`** доказывает, что токен выдан этим сайтом на этот
  вход, а не подсунут другой страницей. Отсюда требование к `MOODLE_URL`: при другом
  написании адреса подпись не сойдётся.
- **Отдельный профиль Chrome**: порт отладки открывается только на нём, личный профиль
  с его cookies команда не трогает.
